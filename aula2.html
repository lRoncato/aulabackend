ANTES DE INSTALAR QUALQUER COISA

O que é uma "biblioteca"?

Biblioteca (ou "pacote") é um código pronto que outra pessoa já escreveu — a gente só usa, sem reinventar do zero.
PENSA ASSIMPra furar uma parede, você não inventa uma furadeira — compra uma pronta. Biblioteca é a "furadeira" de um problema que alguém já resolveu.
▸
Rodar npm install alguma-coisa é baixar uma biblioteca pronta pro projeto.
▸
O Knex, que vamos instalar já já, é uma biblioteca: alguém resolveu "conversar com o banco" — a gente só usa.
A gente não reinventa a roda: usa a que já existe e foca no que é específico do nosso projeto.

OBJETIVO

Conceito fundacional — sem isso, "vamos instalar uma lib" não significa nada pra quem nunca programou.

CONDUZA ASSIM

  • Pergunte se alguém já usou um app que tem "plugins" ou "extensões" (ex.: extensão de navegador) — é a mesma ideia: alguém fez uma peça pronta que você encaixa.

GUARDANDO DE VERDADE

Por que um Query Builder?

Dá pra mandar SQL puro pro banco. Mas montar essas strings na mão, à mão, é chato e arriscado.
SQL NA MÃO"INSERT INTO users (name, email)
VALUES ('"+name+"', '"+email+"')"

fácil de errar a sintaxe e abrir brecha pra SQL injection.
COM KNEXknex('users').insert({ name, email })

é só JavaScript — o Knex monta o SQL certinho por baixo.
Query builder = escrever no banco em JS/TS, sem montar SQL na unha.

OBJETIVO

Justificar a ferramenta antes de instalar — Knex não é "mais uma lib", resolve um problema real (segurança + produtividade).

CONDUZA ASSIM

  • Se perguntarem "é um ORM?": não — Knex é um query builder, mais próximo do SQL. Não mapeia objetos pra classes como Prisma/TypeORM.

MÃO NA MASSA · TODO MUNDO JUNTO

SQLite: o banco é um arquivo

Nada de servidor, Docker, usuário ou senha. O banco inteiro mora num arquivo dentro do projeto: db.sqlite.
POSTGRES / MYSQLUm programa separado, sempre ligado, com porta, usuário e senha.
SQLITEUm arquivo. Quem abre e escreve nele é a própria API.
Não instala nada no sistema, então funciona mesmo em PC sem sudo.
E O ARQUIVO?O db.sqlite nasce sozinho na primeira vez que rodarmos a migration.

OBJETIVO

Apresentar o banco da aula sem precisar de Docker nem permissão de administrador.

CONDUZA ASSIM

  • O SQL é praticamente o mesmo do Postgres. O que muda é onde o banco mora: num arquivo, não num servidor.
  • Se perguntarem "dá pra usar em produção?": dá pra muita coisa, mas sistema com muita gente escrevendo ao mesmo tempo costuma ir pra Postgres. Como usamos Knex, trocar depois é mudar a config, não o código.

FALANDO COM O TERMINAL

O que é um "CLI"?

CLI = Command Line Interface — um jeito de controlar um programa digitando comandos, em vez de clicar em botões.
APP COM BOTÃOClica num ícone, preenche um formulário, aperta "OK".

A CONEXÃO

Criando a conexão

▤ src/config/database.ts import knex, { type Knex } from "knex" export const config: Knex.Config = {   client: "better-sqlite3",   connection: { filename: "./db.sqlite" },   useNullAsDefault: true,   migrations: { directory: "./src/shared/database/migrations" }, } export const connection = knex(config)
import
traz a função knex e o tipo Knex do pacote
export const config
cria a “planta” e deixa outros arquivos usarem
client
qual banco estamos falando (e qual driver usar)
filename
onde fica o arquivo do banco
useNullAsDefault
coluna sem valor no insert vira NULL
migrations
onde o histórico de mudanças do banco mora
export const connection
liga a planta e exporta a conexão pronta pra usar
O config é a "planta" de como conversar com o banco; o connection é a conexão construída a partir dela.

OBJETIVO

Material original do professor — caminho do banco hardcoded aqui de propósito, pra criar o gancho da aula (variáveis de ambiente) mais pra frente.

CONDUZA ASSIM

  • O caminho "./db.sqlite" é relativo a onde o comando roda. Como sempre rodamos npm na raiz do projeto, o arquivo nasce ao lado do package.json.
  • useNullAsDefault: true: o SQLite não aceita a palavra DEFAULT num insert. Sem isso, o Knex mostra um aviso amarelo no terminal. Não é erro, mas assusta.
  • Sem pool aqui: o SQLite é um arquivo, não um servidor com várias conexões.

ANTES DO COMANDO

O que é uma migration?

É um arquivo com uma instrução de mudança na estrutura do banco. Tipo uma receita: "crie a tabela users", "adicione a coluna email".
SEM MIGRATIONVocê cria a tabela na mão, no seu PC. O colega baixa o projeto e o banco dele está vazio. "Na minha máquina funciona!"
COM MIGRATIONA mudança fica escrita num arquivo, junto com o código. O colega roda um comando e o banco dele fica igualzinho ao seu.
▤ src/shared/database/migrations · cada arquivo = um passo 20261005_create_users.ts      → passo 1: cria a tabela users 20261012_add_phone_to_users.ts → passo 2: adiciona a coluna phone 20261020_create_products.ts   → passo 3: cria a tabela products
▸
O número no começo é a data e hora: garante que os passos rodem sempre na ordem. E o Knex anota quais já rodaram, então nunca roda o mesmo passo duas vezes.
Pense no save do videogame: cada migration é um checkpoint do banco. Dá pra avançar (up) ou voltar um checkpoint (down).

OBJETIVO

Dar o conceito antes do comando. Quem nunca programou não tem a dor de "banco diferente em cada máquina", então a comparação sem/com migration é o centro do slide.

CONDUZA ASSIM

  • Comece pela dor: "imagina que eu crio uma tabela no meu PC. Como vocês ficam com ela no de vocês?" Deixe a turma responder antes de mostrar o painel.
  • Na lista de arquivos, aponte que ninguém edita uma migration antiga: precisou mudar algo, cria uma nova (o passo 2 adiciona phone, não altera o passo 1).
  • Outra analogia que funciona: o histórico de uma reforma. Cada anotação diz o que foi feito; quem chega depois segue a lista e chega na mesma casa.
  • O Knex guarda o controle numa tabela própria, knex_migrations. Vale mostrar quando abrirmos o db.sqlite no VS Code.
  • Não aprofunde up/down aqui: isso é o slide "Anatomia de uma migration".

DEFININDO AS COLUNAS

Criando a tabela users

▤ up(knex) await knex.schema.createTable("users", (table) => {   table.uuid("id").primary()   table.string("name").notNullable()   table.string("email").notNullable()   table.string("password").notNullable()   table.boolean("status").defaultTo(true).notNullable()   table.timestamp("created_at").defaultTo(knex.fn.now()).notNullable() })

ANTES DE GUARDAR SEGREDOS

O que é uma "variável de ambiente"?

É um valor que mora fora do código — guardado no computador (ou servidor) onde a aplicação roda, não dentro dos arquivos que a gente escreve.
PENSA ASSIMUma receita de bolo diz "asse na temperatura do SEU forno" — porque cada forno é diferente. A receita (o código) não muda; o ajuste (a variável) é configurado em cada lugar onde ela roda.
▸
No nosso caso, "qual é a senha do banco" muda dependendo de onde o projeto está rodando — seu computador, o servidor da prefeitura, etc.
▸
A variável de ambiente deixa isso configurável, sem precisar mudar uma linha de código.

OBJETIVO

Dar nome e forma ao conceito antes de instalar a biblioteca que lida com ele (dotenv) — sem isso, "variável de ambiente" é só jargão decorado.

E SE ALGUÉM ESQUECER DE CONFIGURAR?

Por que validar as variáveis?

As variáveis de ambiente ficam fora do código — então nada garante que vão estar lá, escritas certinho, quando o projeto rodar em outra máquina.

RESPOSTAS

O número que volta: status HTTP

Toda resposta vem com um número que diz como foi. Começou com 2 = deu certo. Começou com 4 = o pedido tem problema.
200OK
deu certo, toma os dados
201Created
criei o que você pediu
204No Content
deu certo, nada pra mostrar
404Not Found
não achei isso
Quando a gente só faz return, o Fastify manda 200 sozinho.

OBJETIVO

Dar sentido aos números que aparecem na ferramenta de teste.

CONDUZA ASSIM

  • Todo mundo já viu o 404 em site quebrado: use isso de gancho.
  • Se perguntarem do 500: é erro do servidor (bug no nosso código). O detalhe aparece no terminal do npm run dev.
  • Tabela completa pra curiosos: http.cat (cada código com uma foto de gato).
